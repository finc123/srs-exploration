# Meta Muse: methodology

_Generated by `build_json.py` from `sections.py`. Edit the methodology there, not here._

Every series is published **daily** and as **TR7D**, the mean of the 7 calendar days ending on each date. TR7D is left empty unless all 7 days are present and inside that source's complete-through date, so a partial week never reads as a drop. Ratios (per million, shares) are computed from 7-day sums, not by averaging daily ratios.

Muse launched on 2026-09-08. Card and e-receipt windows start 2026-08-01 to give a pre-launch baseline; SensorTower starts 2026-06-01.

**Why two sources for subscriptions?** They see different halves of the market: card panels see web sign-ups billed directly by Meta (`METAPAY META.COM`), but Apple card descriptors carry no app name. E-receipts see App Store and Google Play subscriptions by name, but Meta's own web billing sends no receipt the panel captures. Neither is double-counted against the other.

Complete-through dates for this build: cards 2026-10-16, e-receipts 2026-10-19.

## Launch benchmark: US downloads and DAU by day since launch (SensorTower)

`sections.launch_benchmark`

**Source.** SensorTower SENSORTOWER.COMMON.CORE for Muse, Sora, Threads, ChatGPT and Claude. Clubhouse will be added once it is in CORE.

**Filters.**

| Rule | Why |
|---|---|
| Unified product keys: Muse 6aa0b99dd70c1a09e42dc613, Sora 68dc489f4e04a24f7d0d0aeb, Threads 64a72c98ad4adb0e06dbc506, ChatGPT 64665f59b3ae2712001279ed, Claude 663279a2b3ae277df21f2bd0 | Matched by key, never by name (clones share names). |
| US only; iPhone + Android phone | iPad excluded, as in every SensorTower section. |
| Day 0 = first day with downloads; window day 0 to 120 | Each app's CORE history starts on its launch day. |
| Muse day 0 = 2026-09-08 (public launch) | SensorTower's first Muse day, 2026-09-07, is a partial pre-launch day (about 8k US downloads against about 115k on launch day), so day 0 is the first full day. Those ~8k downloads are left out of Muse's cumulative total, which understates it by under 1% after the first week. |

**Deduplication.** Summed per app and day.

**Measure.** DOWNLOADS = estimated first-time US downloads; CUM_DOWNLOADS = running total from day 0; DOWNLOADS_TR7D = mean of the last 7 days. DAU = estimated US daily active users that day. RETENTION = DAU / CUM_DOWNLOADS on the same day: a proxy for the share of everyone who has downloaded the app who is still using it daily. It is not cohort retention (re-installs and multi-device users blur it) and is best compared across apps at the same day since launch. Muse has fewer days than the others.

**Lag.** Downloads run to about T-2 and DAU to about T-3; the latest DAU day arrives as 0 and is treated as missing.

## Engagement: time spent, US, by day since launch and over the last 90 days (SensorTower)

`sections.time_spent`

**Source.** SensorTower SENSORTOWER.COMMON.CORE (sessions and minutes from SensorTower's cross-platform daily session estimates), for the launch benchmark apps: Muse, Sora, Threads, ChatGPT, Claude.

**Filters.**

| Rule | Why |
|---|---|
| Same apps, keys, US scope and day 0 as the launch benchmark (Muse day 0 = 2026-09-08) | So the time-spent view lines up with the benchmark above it. |
| Clubhouse not shown | Clubhouse is not in SensorTower CORE yet, so it has no session or time-spent data here. |
| Sora in Days since launch only | CORE has no Sora rows after 2026-03-24 (checked 2026-10-12), so it has no last-90-days data. |
| Days since launch: day 0 to 120. Last 90 days: the 90 calendar days ending on the latest day with minutes | The first compares each app's launch period; the second compares the apps as they are today. |
| Zero sessions, minutes or DAU = missing | SensorTower's latest days arrive as 0 before they are filled in, so a zero is not a real value. |

**Deduplication.** iPhone and Android phone summed per app and day.

**Measure.** SESSIONS_PER_DAU = sessions / DAU: how many times an average daily user opens the app (a session is each time the app is opened). MIN_PER_SESSION = minutes / sessions: the average session length. MIN_PER_DAU = minutes / DAU: average daily time per active user, which also reflects how often users open the app. The *_TR7D ratios are 7-day sums over 7-day sums (minutes over sessions or DAU, sessions over DAU), not means of daily ratios, over the days in the window where both values are present; early days since launch use fewer than 7 days. Modelled vendor estimates, best read as trends.

**Lag.** Sessions and minutes arrive about a week after DAU (on 2026-10-12 they ran to 10-03, DAU to 10-09), so the last 90 days end earlier than the DAU charts. The TR7D line stops at each app's last day with minutes.

## Engagement: web minutes per visit, US (SimilarWeb)

`sections.web_time_spent`

**Source.** SimilarWeb SIMILARWEB.COMMON.VISITS_V2 (the SimilarWeb pipeline's consumer table): all_traffic_time_spent (total minutes = visits x average visit duration) and all_traffic_visits.

**Filters.**

| Rule | Why |
|---|---|
| Domains muse.ai, chatgpt.com and claude.ai; desktop plus mobile web, subdomains included | Muse's web app against the two assistants in the app benchmark. chatgpt.com includes chat.openai.com, which the pipeline sums into it. |
| US only | Same scope as the app time-spent chart. |
| Muse from 2026-09-08 (public launch) | Pre-launch muse.ai traffic is not Muse usage. |

**Deduplication.** One value per site and day.

**Measure.** MIN_PER_VISIT = time spent / visits: the average visit length in minutes. MIN_PER_VISIT_TR7D = 7-day time spent over 7-day visits (weighted by visits, not a mean of daily averages), over the days with both. A SimilarWeb visit lasts until 30 minutes idle, while an app session is each time the app is opened, so compare sites with each other, not with the app chart. Modelled vendor estimates, best read as trends.

**Lag.** Vendor series, about T-3. The TR7D line stops at each site's last day with time spent.

## Muse digital ad spend (Pathmatics)

`sections.ad_spend_daily`

**Source.** Pathmatics PATHMATICS.COMMON.DIGITAL_AD_SPEND (estimated digital ad spend by advertiser, publisher, region and day).

**Filters.**

| Rule | Why |
|---|---|
| Advertiser 'Muse from Meta' | Pathmatics tracks Muse as its own advertiser, separate from Meta AI and Meta's other brands. |
| Region United States or Canada | Muse is live in the US and Canada only; other regions carry negligible spend. |

**Deduplication.** Summed per day, country and publisher.

**Measure.** SPEND = estimated US$ spend. A day with no row is no observed spend. Pathmatics covers digital channels only, not TV, and the team suspects budget has moved to TV, so a fall here is not a fall in total marketing.

**Lag.** Vendor series; the latest day shown is the latest Pathmatics has published (about T-3).

## Muse web subscriptions (card panels)

`sections.muse_web_daily`

**Source.** Yodlee card & bank panels, feeds 3, 4 and 6 (SHARE_CE_SPEND_201_PRIME_EX_TAU). Feeds 1 and 2 stopped in 2025-09. The 279 panels are not used: 279 PRIME is a subset of these Yodlee feeds, the other 279 schemas are mirrors, snapshots or stale, and 279 PRIME_TAU showed no web Muse charges.

**Filters.**

| Rule | Why |
|---|---|
| Description contains METAPAY and META.COM (e.g. 'METAPAY META.COM CA') | Meta bills web subscriptions directly under this descriptor. Muse has no app-name in the descriptor, so the descriptor alone identifies Meta direct billing, not Muse. |
| Exclude METAPAY* / METAPAY * (with an asterisk) | That form is Meta Pay: ad payments and peer-to-peer transfers, not subscriptions. |
| Amount $15.99-17.60 (Power) or $79.99-88.00 (Max) | Muse web list prices are $16 and $80; the upper bounds allow for sales tax. The same descriptor carried legacy $11.99 / $12.99 charges before launch and occasional off-price charges (e.g. $15.90 on 2026-09-11), so the price bucket is what isolates Muse. In-app prices ($20 / $100) never bill under this descriptor. |
| Not matched: GOOGLE *FACEBOOK, Apple, PP*METAPLATFOR, FACEBK * | Google Play bills every Meta app as GOOGLE *FACEBOOK, so its small launch uplift cannot be isolated from other Meta subscriptions (investigations/android_crosscheck.ipynb), Apple card descriptors carry no app name, and the PayPal / FACEBK forms are ads and Quest. In-app Muse is measured from e-receipts instead. |

**Deduplication.** Distinct (member, day, amount, plan): Yodlee pending and posted copies of one charge can carry different transaction ids.

**Measure.** MEMBERS = distinct panel members charged that day, per plan. TXNS = deduplicated charges. A charge is a new subscription or a monthly renewal. Web Muse first charges appear around 2026-09-17, nine days after launch; the cause is not confirmed (possible billing delay, trial or slow web adoption).

**Lag.** Complete through run date minus 5 days; later days are excluded.

## Muse in-app subscriptions (e-receipts)

`sections.muse_inapp_daily`

**Source.** NIQ e-receipts, SRS_SLICE.COMMON.ITEMS_LIVE (the processed NIQ line-item table, one row per receipt line item, with mailbox status), via the SRS_MCP.META.MUSE_NIQ_RECEIPTS view.

**Filters.**

| Rule | Why |
|---|---|
| Active mailboxes only (mailbox_status = 'active') | Inactive mailboxes have disconnected or stopped syncing, so their receipt history stops. Keeping them would mix panel churn into the trend; this is the SRS convention for NIQ (e.g. the Roblox bookings slice). It removes 11 of 275 Muse mailboxes as of 2026-10-07. |
| Description contains 'Muse from Meta' | The App Store / Google Play receipt names the subscription. 'Muse' alone also matches other apps and museums; the pre-launch 'Meta One' Core / Premium plans are a different product. |
| Merchant iTunes* -> Apple, Google Play* -> Google Play; other merchants dropped | In-app subscriptions are billed by the store. No direct-from-Meta Muse receipts exist (Meta receipts near $16 are Quest games and Instagram boosts), so web Muse is measured on cards. |
| Plan from the description: 'power' -> Power, 'max' -> Max, else Other | In-app list prices are $20 (Power) and $100 (Max); the plan name is more reliable than the amount, which varies with tax and occasional $28 regional prices. |
| Kind: cancel (merchant or text says cancel / 'will end on'), trial ('trial'), else charge | Stores send separate receipts for trial starts and cancellation confirmations. |

**Deduplication.** Distinct mailboxes per day, store, plan and kind (a receipt can repeat across line items).

**Measure.** CHARGES = mailboxes with a paid Muse receipt that day; CANCELS = cancellation notices; TRIALS = trial-start receipts.

**Lag.** Complete through run date minus 2 day.

## Muse in-app subscriber flows (e-receipts)

`sections.inapp_flows_daily`

**Source.** The in-app e-receipts above (same filters: active mailboxes, 'Muse from Meta', Apple / Google Play).

**Filters.**

| Rule | Why |
|---|---|
| Gross add = the day of a mailbox's first charge receipt, per store and plan | Every mailbox's first paid Muse receipt is a new subscriber; later charges are renewals. The window starts before launch, so no subscriber predates it. |
| Cancel = a cancellation-confirmation receipt | Stores email a confirmation when a user cancels; the plan usually runs to the end of the paid period, so a cancel is a churn notice, not an immediate loss. |
| Trial-start receipts are left out | Muse is freemium, trials are not a standard offering, and the few trial receipts were judged noise (team review, 2026-10-07). |

**Deduplication.** One first charge per mailbox, store and plan; cancels are distinct mailboxes per day.

**Measure.** GROSS_ADDS = new paying mailboxes that day. CANCELS = cancellation notices. NET_ADDS = GROSS_ADDS - CANCELS. A plan switch counts as a gross add on the new plan. Whether Google Play and Apple both send a receipt for every renewal is under investigation, so renewals are not shown here.

**Lag.** Complete through run date minus 2 day.

## Muse web subscriber flows (card panels)

`sections.web_flows_daily`

**Source.** The web Muse card charges above (Yodlee feeds 3, 4 and 6, same descriptor and price filters), plus each charged member's panel activity: the days they transacted with any merchant in the same panels (muse_member_panel). There is no card-panel active-member table to reuse (srs_slice.common.normal_active is NIQ mailboxes only), and Yodlee's own membership tables (LAST_REFRESH, ACCOUNT_ATTRIBUTES) are incomplete: on 2026-10-09 they were missing 15 and 26 of 69 payers who were still transacting daily.

**Filters.**

| Rule | Why |
|---|---|
| Gross add = a payment with no payment in the previous 35 days, by a member first seen transacting in the panel more than 35 days earlier | Cards have no sign-up event, so a new subscription is a payment after a gap. The membership test stops an existing subscriber who has just joined the panel from counting as a sign-up; those payments are NEW_TO_PANEL instead. |
| Cancellation = no payment within 35 days of a member's last payment, dated at last payment + 35 days, if the member is active: at least one transaction with any merchant in the 30 days ending on that date | Monthly plans renew about every 30 days, so a missed renewal means the plan ended. The activity test separates Muse churn from panel churn, and its window sits wholly inside complete data, so a recent lapse needs no settling period. |
| Panel exit = the same lapse by a member with no transaction in that window; the gross add that started their subscription is then removed (EXITED_ADDS) | A member who has left the panel tells us nothing about whether they cancelled, so neither their lapse nor their sign-up is counted. This rewrites history: a gross add drops off its original date once the member is found to have left. |
| A lapse ending a subscription that began as NEW_TO_PANEL is UNSEEN_LAPSES, not a cancellation | We never saw that subscription start (the member joined the panel already subscribed), so it has no gross add; counting its end as a cancellation would bias net adds down. Both ends of a subscription are counted only when we saw it start. |
| Renewal = a payment within 35 days of the member's previous payment | The sequence is per member across plans, so a Power-to-Max switch counts as a renewal on the new plan, not a gross add. |

**Deduplication.** Distinct (member, day, plan), as for subscriptions.

**Measure.** GROSS_ADDS, CANCELS and NET_ADDS = GROSS_ADDS - CANCELS per day and plan; RENEWALS, NEW_TO_PANEL, PANEL_EXITS, EXITED_ADDS and UNSEEN_LAPSES complete the reconciliation (every payment is a gross add, exited add, renewal or new-to-panel; every lapse a cancellation, panel exit or unseen lapse). The first web payment was 2026-09-17, so the first possible cancellation is 2026-10-22.

**Lag.** Complete through run date minus 5 days; a cancellation appears once its date is inside that window.

## Agentic Checkout to Non-Stripe Merchants

`sections.agentic_daily`

**Source.** Prime Omega (SHARE_CE_PRIME_ENRICHED_OMEGA_2822.PRIME_OMEGA TRANS_V1_0 joined to MID_V1_0 for the descriptor), all cardlinks rather than the 2022 consistent-shopper panel, which holds only ~15% of agentic rows. Omega replaced Yodlee feeds 3/4/6 on 2026-10-19: it is a superset (97% of Yodlee agentic transactions have an Omega transaction of the same amount within 3 days) with 1.45x the agentic volume. Web Muse stays on Yodlee.

**Filters.**

| Rule | Why |
|---|---|
| Description contains LINKAGNT* | Stripe Link's agent-wallet descriptor ('LINKAGNT* <merchant> WWW.LINK.COM CA'), used until 2026-09-23. |
| Or LINK* followed by a space, at the start of a word | From 09-23/24 Stripe shortened the descriptor to 'LINK* <merchant>'. No Stripe URL/city anchor is required: Duffel airline bookings ('LINK* DELTA AIR DUFFEL.COM NY') and truncated card descriptors ('LINK* GO PUFF*GB LIC.') carry neither, and add ~15%. LINK.COM* (the ordinary Link wallet), EVENTLINK* and CLINK* fail the 'space after *' / word-start rules. |
| Not cash app, missing link*, pto link*, debt-link*, team link*, coffee link*, visa money | Unrelated billers that also contain 'LINK* ' (Cash App, PTO Link, Debt-Link...): about 1-2 a day before launch, which is the false-positive floor. |
| Amount > 0 | Purchases only; refunds (about 2% of rows) are negative and excluded. |

**Deduplication.** Distinct (source, transaction id).

**Measure.** TXNS = agentic purchases that day; SPEND = their $ total; MEAN_SPEND = SPEND / TXNS (MEAN_SPEND_TR7D is 7-day spend over 7-day count). PER_MILLION = TXNS per million Omega transactions that day. Panel coverage still fills in for ~10 days, so the rate is the comparable series and raw counts in the latest days run low. PER_MILLION_TR7D is the ratio of 7-day sums, not a mean of daily ratios. The count is a floor: at merchants that take Stripe directly, an agent purchase carries the merchant's own descriptor and is invisible here; at the top agentic merchants Link-agent rows are under 0.01% of panel transactions (0.5% at Porkbun) since launch (investigations/stripe_vs_link_share.ipynb).

**Lag.** Complete through run date minus 5 days.

## Top agentic-checkout merchants (since launch and trailing 28 days)

`sections.agentic_merchants`

**Source.** The agentic transactions above.

**Filters.**

| Rule | Why |
|---|---|
| Merchant = the 2-12 characters after the LINKAGNT* / LINK* prefix (and any SP / DD * / QDI* processor prefix) | Descriptors truncate merchant names, so this is a label for reading, not an entity match. |

**Deduplication.** As above.

**Measure.** Purchases only (amount > 0). A breakdown table rather than a daily series: the top 25 merchants by transactions, with unique cardholders and median amount, for two windows ending at the card complete-through date: PERIOD = 'Since launch' (from 2026-09-08, growing each day) or 'Last 28 days'. CARDHOLDERS = distinct panel members (per source); TXNS well above CARDHOLDERS means repeat agent purchases by the same people. SPEND_SHARE = the merchant's agentic $ over all agentic $ observed in the same window (every Link-agent transaction, including the few with no readable merchant label), so it is a share of observed agentic spend, not of the merchant's total sales.

**Lag.** Complete through run date minus 5 days.
